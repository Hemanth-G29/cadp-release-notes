2. Release Summary

This release of CADP Workspace Version 1.0.0 (29) delivers 34 bug fixes, 3 new features, and 10 enhancements across the platform. Highlights include A formula returning a list no longer fails silently, and DISTINCT_* works, A formula field now means the same thing wherever the write came from, and Validate Expression warns when a formula returns a list. Refer to the Known Issues section for current limitations.

3. New Features

Feature IDFeature NameDescriptionImpact
A formula returning a list no longer fails silently, and DISTINCT_* worksThree related changes to how the engine handles a formula that produces many values; rather than one. Raised by QA, who read an empty field as a broken formula.; 1. **A list-returning formula is now called out.** `UNIQUE()`, and any aggregate given a; groupBy, returns a list; a formula field shows one value, so the field renders blank.; Validate Expression now shows a warning saying so, and evaluate-form-batch returns `null`; plus an `errors[]` entry naming how many values came back. Previously the field simply went; blank with `errors: []` - indistinguishable from a formula that legitimately produced; nothing. The formula still SAVES: it is not wrong, it just cannot be displayed.; 2. **An aggregate handed a list is refused.** `COUNT_RECORDS(UNIQUE({price}))` reads like; "count the distinct prices" and answered 0. The field token is quoted only for the OUTER; aggregate, so the nested call received `{__aggN}` unquoted, resolved nothing and returned an; empty list for the outer one to count. It is refused at validate time, naming the; `DISTINCT_*_OF_RECORDS` function to use instead. Deliberately NOT made to work: counting a; list would give COUNT_RECORDS two meanings over the same data (4 records, 2 distinct) and; leave its filter argument ambiguous.; 3. **The DISTINCT_* family now works at all.** Two faults, the first hiding the second.; `isInsideAggregateCall` and `isAggFilterArg` matched six names, and; `DISTINCT_COUNT_OF_RECORDS` contains `COUNT_OF_RECORDS`, not `COUNT_RECORDS`, with no word; boundary after `DISTINCT_` - so none could ever match it, and its field token was treated as; an ordinary single-record lookup that matched every record: "Multiple records found". Past; that, the evaluator read only `__featureRecords__`, while the resolver had already fetched; the values and substituted them as `{__aggN}` - the way the PLAIN aggregates receive them -; so it answered 0. It now reads that array, de-duplicates, and applies the same metric; (hoisted to a shared `distinctApply` rather than duplicated).
A formula field now means the same thing wherever the write came fromone shared recalculation service (`formulaProjection.service.js`) used by every; path that writes a record, plus an internal endpoint the workflow service calls after it; writes.; Before this, which fields a write recalculated depended on the door it came through:; | Write path | Where formula fields got their value | Correct for the whole language? |; |---|---|---|; | Manual create / submit | `unified-event-processor.js` → `applyProjectionFormulas` | yes |; | Bulk import | `importFormula.service.js` → `applyProjectionFormulas` | yes |; | Direct field update | `featureData.service.js` → inline `new Function` | **no — arithmetic only** |; | Workflow record write | nothing | **no — never ran** |; The `new Function` path substituted `{f:uuid}` with numbers and only evaluated when the; result was purely numeric and arithmetic, so `IF(...)`, `ROUND(...)`, `LOOKUP(...)` and every; aggregate silently produced nothing on a direct update (view-cart quantity increment, inline; grid edits) while the same expression worked when submitted. The workflow path wrote straight; to the collection with the driver, so a formula field it touched kept the node's value only; until the record next opened in create mode, where the form recomputed over it.
Validate Expression warns when a formula returns a list`UNIQUE()`, and any aggregate given a groupBy, returns a list of values. A formula; field shows one value, so such a formula renders blank. Validate Expression now shows an amber; warning saying exactly that, instead of the green "Formula is valid" that gave no hint why the; field would stay empty.

4. Enhancements / Improvements

Enhancement IDModuleDescriptionBenefit
data-importThe batch import (`/data/batch-import/upload`) now accepts `lookupPolicy`. In each; 10,000-row batch, rows with missing lookup values wait until after the first lookup pass. All; missing values in the batch are then created with one `importFeatureDataWithMode` call per; referenced feature, with required-field Default Values applied and no-default rows skipped. Only; the waiting rows are checked again, with a fresh lookup cache. A value that fails to create; reports why on its row. `referenceCreated` is stored on the batch job and returned by its status; API. The policy parser and the job-counter helper moved to `src/utils/importLookupPolicy.js`, so; both pipelines use the same code.Lookup features now import through the batch pipeline, which ignored the; Referenced Feature Import box.
data-importWhen an import auto-creates a missing lookup value in the referenced feature, any; required field of that feature that is not in the file now takes its configured Default Value.; If a required field has no Default Value, the record is not created and the row is skipped with; "Record not created in referenced feature "X" for "V": required field(s) A, B have no Default; Value set, so this row was skipped." Unique, auto-generated and session-param fields are never; filled from a default. The import status now returns `referenceCreated`; (`[{ featureId, featureName, count, defaultsApplied[], skipped, missingDefaults[] }]`), totalled; across chunks. Applies to the chunked import (Pipeline A), for lookup fields and reference-table rows.Auto-create failed on every referenced feature that had any other required field.
data-importOn the batch import path, a matched row whose file values already equal the stored record; (e.g. Country Code IND, Currency INR → stored INR) is no longer written or counted as Updated. It is; counted in a new `unchangedCount` (job doc, `/batch-import/:jobId/status`) and the Import modal shows; "Same record, no changes: N" under Created / Updated; "Successfully Imported" includes it.; Comparison is `isPatchUnchanged` (utils/batchImportMatch.js): values compare as text (`10` = `"10"`),; objects by JSON, encrypted fields by the stored `_hash` (missing hash = changed). A row carrying; reference-table rows always counts as changed. Unchanged rows are not sent to onUpload workflows.Re-importing an exported file reported every matched row as Updated even when nothing changed.
data-importFeatures whose dropdown is sourced from another feature's records (e.g. Inventory →; Product Name) now import through the batch pipeline (10,000 rows per write) instead of the; chunked one; only features with a table still use the chunked pipeline. Lookup resolution now; queries each distinct value once per chunk / batch instead of once per row (`findLookupMatches`; memoizes hits in the existing per-chunk/per-batch context cache, keyed by target feature + built; query clauses). Misses are not cached, so a record auto-created mid-import is still found on; re-inspect.Importing such a feature sat at 0% for a long time — the chunked path reports progress; only per finished 100-row chunk, and each row ran its own unindexed lookup query plus a per-row save.
data-importImporting a feature with a lookup/reference dropdown is now about as fast as one without.; Before the per-row loop, `prefetchLookupMatches` collects each lookup field's distinct values,; fetches the matching source records with one `$in` query per 2,000 values; (`LOOKUP_PREFETCH_VALUES_PER_QUERY`), pairs them in memory (strict equality, array fields match; by containment, same as MongoDB) and seeds the per-batch cache `findLookupMatches` reads. Row; results, ambiguity (2+ matches) and error messages are unchanged. Unsupported clause shapes; (dotted/operator aliases) and query errors fall back to the per-row path. Misses are cached unless; lookup auto-create is on. Used by both the batch and the chunked pipeline.20,000 rows with 13,166 distinct Product Names meant ~13,000 unindexed scans of the; source feature, one per row. Measured after the change: 20,000 rows imported in 24 s.
feature-data-exportLayout/display components (e.g. "2 Column Grid", type `column-grid`) no longer appear as empty; columns in exported files. Field defs now skip every type in the shared; `NON_ATOMIC_COMPONENT_TYPES` set (tables exempted — export handles them separately).; Excel exports: the header row of every sheet (Records + table detail sheets) is locked via sheet; protection; data cells and new rows stay editable (insert/delete rows, sort, filter allowed), so the; file can still be edited and re-imported. No password — guards against accidental header edits only.The export's local blocklist only had `grid`/`column`/`row`…, not `column-grid`, so grids; leaked into the header row. Header lock requested to keep the import-matching headers intact.
component-properties`ADVANCED_SECTION_VISIBILITY` lists `'Interactions': ['*']` (last, so it is added after every; other Advanced section). New `ADVANCED_SECTION_FIELDS` gives a section added through that list its fields; (only Interactions has any; every other section is still added with `fields: []`). The fields live in the; new `src/seeders/interactionSectionFields.js`: ≈235 entries `{ key, label, type: 'custom' }`, some with; `options: [{ value, label }]` naming the saved values of a dropdown. `{name}` in a label is filled by the; builder. No `defaultValue` on any of them (they are words, not settings — the table column drop copies; field defaults into `componentProps`).; `withEveryTypeSections` also adds such a `'*'` section (last) to each type's own document in the base-doc; pass: a type missing from the components list (e.g. `image`, `select`, `row`, the charts) never reaches; `buildMergedGroups`, and the API adds only `__common__` to it — the first seed run left ≈100 types; without Interactions, which the builder used to force onto every component. Dry-run of the whole seeder; (Mongo stubbed) against the previous version: all 144 written types identical apart from the added; Interactions; every type has it, last. Not touched: 54 leftover documents of types no longer seeded or in; the palette (July–September).Interactions was the only Advanced section the builder added by itself, with its words hard-coded.; Now it is listed, and worded, by the component properties like the rest.
data-importRestored the "Referenced Feature Import" checkboxes in `ImportTransactionsModal`. The; chunked upload sends `lookupPolicy` again, so ticking a box really creates missing values. The; import summary now has a "Referenced features" section under Created / Updated / Same record:; "Created in X: n", which required fields got their Default Value, and "Skipped in X: n" with the; required fields that have no Default Value.Auto-creating records in referenced features is needed again.
formula-field-properties`DISTINCT_COUNT_OF_RECORDS()` and its four siblings now appear in the Aggregate; category of the formula builder's **Operators and Functions** tab, beside the five that were; already there.that tab holds its own hardcoded list, separate from autocomplete and from Help. The; DISTINCT family has never been in it - checked with `git log -S`, this is not a removal - so the; only ways to reach those functions were typing the name and accepting the completion, or reading; Help. Anyone browsing the list to find "count the distinct values" found nothing and concluded; the platform could not do it.
interaction-properties**The section is listed by the component properties, like every other Advanced section.** The builder used; to add "Interactions" itself to every component (`[...apiAdvancedOrder, 'Interactions']`, an; `Interactions: {}` key, `'Interactions': ['*']` in the frontend visibility list, and two; `sectionName === 'Interactions'` exceptions). All removed: the rbac seeder now lists it for every; component type, last, so it shows in the same place as before.; **Every word of the panel is read from that section** (≈235 fields: labels, hints, placeholders, empty /; loading / error messages, the names in its dropdowns, and the notes above the panel for a carousel; slide, navbar item, listing button, navbar container and listing card). Covers InteractionProperties,; PassDataFieldMap, ShopperChoiceActionSection, ShowOnlyPartsPicker, ListingBarActionInteractions and the; notes in advancedFieldsProp. `interactionWords.tsx` gives them the words (`InteractionWordsProvider`,; `useInteractionWords`, `readInteractionWords`): `t(key, values)` fills `{name}`, `rich` places nodes; (bold names), `optionLabel(key, value)` names a saved value. A word the section lacks shows as nothing —; never a made-up text.; **The code keeps the values and the steps; the section keeps the words.** Dropdown values (`onClick`,; `navigate`, `eq`, `sm`, …) are unchanged and saved as before; only their shown names come from the; section's `options`. Problem messages under a mapping are now picked by key (`issueNoMaster`, …).; Dropdowns that used to show raw code words now show names: Trigger (Click, Double click, …), Action; (Navigate, Open popup, Save shopper choice, …), Navigation Target, Feature Page Mode, Record Source.Interactions was the only Advanced section not defined in the database — added by code to every; component, with ~320 hard-coded words. Now it follows the same pattern as the rest, and its words are; changed in the seed, not in code.
